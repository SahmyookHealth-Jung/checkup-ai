# 4단계 투어: RAG 해설이 도구마다 어떻게 보이는가

4단계(ADR 0007)에서 만든 흐름을 직접 실행하며 눈으로 확인하는 안내다. 순서대로 따라 하면 30분 안팎이 걸린다.
Haiku 호출이 들어가는 단계에는 비용을 적었다(보고서 하나에 약 $0.0025).

```
결과지 PDF → 추출(Haiku) → 국가 기준 판정(코드) → 근거 검색(bge-m3 + pgvector) → 해설(Haiku) → 검증·고정 문구(코드) → 화면
```

## 0. 준비

```bash
docker compose up -d                                      # PostgreSQL + pgvector (저장소 루트에서)
cd eval && .venv/bin/python -m rag.build_chunks && cd ..  # 근거 청크 만들기 (모델 호출 없음)
cd backend && ./gradlew :app:bootRun                      # 앱 실행 (다른 터미널에서 아래를 진행)
curl -X POST localhost:8080/api/guidelines/reload         # 청크 83개 적재 (CPU에서 약 1분 반)
```

## 1. 글이 벡터가 되는 것 보기 (터미널)

로컬 Ollama의 bge-m3에 문장 하나를 보내면 숫자 1,024개가 돌아온다. 이것이 "임베딩"이다.

```bash
curl -s localhost:11434/api/embed -d '{"model":"bge-m3","input":"공복혈당 질환의심"}' | python3 -c "import json,sys; v=json.load(sys.stdin)['embeddings'][0]; print(len(v), v[:5])"
```

- 비슷한 뜻의 문장은 비슷한 숫자 묶음이 된다. 검색은 이 숫자 묶음 사이의 거리(코사인)로 한다.

## 2. 벡터 테이블 들여다보기 (IntelliJ Database 창 또는 psql)

- 연결: localhost:5433, 데이터베이스·계정·비밀번호는 `.env`의 POSTGRES_* 값.
- IntelliJ는 Database 창 → + → Data Source → PostgreSQL로 연결한다.

```sql
-- 청크와 메타데이터
SELECT id, metadata->>'section' AS section, left(content, 60) AS content FROM guideline_chunk ORDER BY id LIMIT 20;

-- 임베딩 차원 확인 (bge-m3 = 1024)
SELECT id, vector_dims(embedding) FROM guideline_chunk LIMIT 3;

-- "공복혈당 판정기준 행"과 가장 가까운 청크 5개 (<=> 는 코사인 거리, 1 - 거리 = 유사도)
SELECT b.id, round((1 - (a.embedding <=> b.embedding))::numeric, 3) AS similarity
FROM guideline_chunk a, guideline_chunk b
WHERE a.id = 'mohw-annex4-row-fasting-glucose'
ORDER BY a.embedding <=> b.embedding
LIMIT 5;
```

- 앱의 검색은 질문 문장을 먼저 임베딩하고, 그 벡터로 같은 `ORDER BY embedding <=> 질문벡터 LIMIT 4`를 한다(Spring AI PgVectorStore).

## 3. 검색 API (터미널)

```bash
curl -sG localhost:8080/api/guidelines/search --data-urlencode 'q=공복혈당(Glucose) 질환의심' | python3 -m json.tool | head -40
```

- 해설 서비스가 만드는 질의 형식이 "항목명 + 판정 구분"이다. score가 유사도이고, 0.5 미만은 근거로 쓰지 않는다.
- 검색 평가: `cd eval && .venv/bin/python -m rag.run_retrieval_eval` (정답셋 20개, hit@4·MRR, 모델 호출 없음).

## 4. 해설 한 번 돌려 보기 (터미널, 약 $0.0025)

```bash
curl -s -X POST localhost:8080/api/demo/samples/sum-001/explain | python3 -m json.tool | less
```

- `explanation.judgments`: 코드가 국가 기준으로 판정한 결과 (LLM 아님)
- `explanation.items[].sentences[].citations`: 문장마다 인용 번호
- `explanation.metrics`: 문장 통과 수, 지운 인용, 금지 표현, 검색·생성 지연

## 5. IntelliJ 디버거로 속 들여다보기

`./gradlew :app:bootRun` 대신 IntelliJ에서 `CheckupAiApplication`을 Debug로 실행하고 중단점을 건다.

| 중단점 | 볼 것 |
|---|---|
| `ExplanationService.generate` | `sources`(LLM에 보내는 근거 문단, 시스템 메시지), `items`(항목·결과값·판정·허락된 근거 번호) |
| `PersonalInfoRedactionAdvisor.adviseCall` | 모델로 나가기 직전 사용자 메시지에서 이름·수검번호가 `[이름]`으로 바뀐 모습 |
| `ExplanationValidator.check` | LLM이 낸 문장 중 인용·숫자 검증에서 버려지는 문장 |
| `ScreeningCriteria.judge` | 값이 판정기준표의 어느 구간에 들어가는지 |

## 6. 화면과 네트워크 (브라우저)

- http://localhost:8080 → 합성 샘플 선택 → "해설 보기"
- 개발자 도구 → Network: `/api/demo/samples/{id}/explain` 요청과 응답 JSON
- 결과 표의 "결과지 판정"과 "국가 기준 판정"을 비교하고, 해설의 [n]을 눌러 출처 원문을 펼쳐 본다

## 7. 호출 기록과 비용 (DB, Anthropic Console)

```sql
SELECT called_at, feature, model, input_tokens, output_tokens, latency_ms, cost_usd, redactions
FROM llm_call_log ORDER BY id DESC LIMIT 10;
```

- 기능별(`report.extraction.first-pass`, `report.explanation`)로 토큰·비용·지연과, 지운 식별정보 개수가 남는다. 원문은 남지 않는다.
- Anthropic Console의 Usage 화면에서 같은 시간대 사용량이 찍히는지 비교한다.

## 8. 평가 스크립트

```bash
cd eval
.venv/bin/python -m rag.run_retrieval_eval            # 검색 기준선 (무료)
.venv/bin/python -m rag.run_explanation_eval --runs 1 # 해설 10개 (약 $0.03)
```

결과는 `eval/results/rag/`에 저장된다. 4단계 기준선 수치는 ADR 0007 "결과"에 있다.
