# 프로젝트 브리프: 건강검진센터 AI 플랫폼

> 2026-11-08 인수인계 내용을 정리한 문서다. 원래 브리프와 달라진 점은 맨 아래 "변경 이력"에 적는다.

## 1. 배경과 목표

- 작성자는 SI 회사에서 1년간 건강검진센터 차세대 프로젝트(C# WinForms + Java Spring Boot)를 했다.
- 목표: AI 역량을 키우고 증명하는 포트폴리오로 취업을 준비한다.
- 포지셔닝: **"AI 기능을 실서비스에 붙이고, 성능을 측정·개선할 줄 아는 Java 백엔드 개발자"**
- 개발에는 Claude Code를 적극적으로 쓴다. 단, 핵심 설계(RAG 구조, 청킹/검색 전략, 평가 지표, 프롬프트/가드레일)는 작성자가 이해하고 결정한다.

## 2. 기능

### 기능 1 (메인): 건강검진 결과 해설 AI (RAG)

- 검진 결과지(PDF/이미지/텍스트)에서 수치를 추출해 JSON으로 구조화한다(Structured Output). → 지금은 글자 층이 있는 PDF와 텍스트만 지원한다. 이미지(스캔)는 하지 않는다(ADR 0003).
- 공개 가이드라인 문서(질병관리청, 국민건강보험공단 등)를 RAG로 검색한다.
- 답변마다 출처를 인용한다. "의료 진단이 아님" 가드레일을 두고, 위험 수치에는 진료를 권고한다.
- 하이브리드 검색(키워드+벡터)과 리랭킹을 쓴다. → 아직 구현하지 않았다. 판정 해설은 조회로 바꿨고, 후속 질문 경로에서 벡터 기준선과 전후를 비교한다(ADR 0010 2절, 순서 6).
- **평가셋 50~100개와 자동 평가(LLM-as-a-Judge 포함)로 개선 전후 수치를 비교한다. ← 가장 중요**

### 기능 2 (후속): 관리자용 Text-to-SQL 통계 어시스턴트

- 데이터: 공공데이터포털 "국민건강보험공단_건강검진정보" (익명화된 샘플)
- SELECT만 허용, 읽기 전용 DB 계정, SQL 검증, 실패 시 재시도, 정확도 평가

## 3. 원칙

- 전 회사의 코드, DB 스키마, 실제 수검자 데이터는 쓰지 않는다. 공공데이터나 합성 데이터만 쓴다.
- 의료 진단을 하지 않는다는 원칙을 기능과 프롬프트에 명확히 반영한다.
- 저비용으로 운영한다. 개발·평가·데모는 저가 API 모델(Haiku 5.5)로 하고, 외부로 보내기 전에 식별정보를 로컬에서 지운다. 데이터를 밖으로 보낼 수 없는 환경을 위해 로컬 모델 경로(오프라인 모드)를 유지한다([ADR 0005](adr/0005-추출-모델-선택.md)).
- Spring AI 설정만 바꿔 모델을 교체할 수 있는 구조로 만든다(Ollama ↔ Claude API).
- API 키는 환경변수나 `.env`로 관리하고 `.gitignore`에 등록한다. 절대 커밋하지 않는다.

## 4. 기술 스택 (확정, 근거는 [ADR 0001](adr/0001-기술스택-선정.md))

| 영역 | 선택 |
|---|---|

| 빌드 | Gradle 9.8 (Kotlin DSL), 멀티모듈 ([ADR 0002](adr/0002-저장소-모듈-구조.md)) |

## 5. 진행 단계

주 단위로 기간을 나누지 않는다. 아래 단계를 순서대로 진행하고, 한 단계의 결과를 확인한 뒤 다음 단계로 넘어간다 (2026-11-10 결정).
한 단계를 깊게 완성하기보다 **얇게라도 끝까지 먼저 잇고**, 그다음 측정하며 깊게 판다. 추출은 2단계에서 닫고, 남은 약점은 ADR의 한계로 남긴다.

| 단계 | 내용 | 상태 |
|---|---|---|
| 1 | 결과지 → JSON 추출과 검증. 처음 보는 양식으로 일반화 수치를 기록하고 ADR 0004를 채택한다 | 완료 (2026-11-10, heldout-v3 F1 0.926) |
| 2 | 모델 × 파이프라인 비교: qwen3:4b·Haiku × baseline·validated의 F1·비용·지연을 한 표로 (ADR 0005) | 완료 (2026-11-10, 기본 모델 Haiku 5.5) |
| 3 | `core` 호출 기록: 모든 LLM 호출의 토큰·비용·지연을 DB에 남긴다. 외부 전송 전 식별정보 제거 규칙도 여기서 정한다 | 완료 (2026-11-10, ADR 0006, 식별정보 잔존율 0%) |
| 4 | 얇은 전체 연결: 가이드라인 몇 개 수집·청킹·적재 → 기본 검색 → 출처 붙은 해설 + 기본 가드레일 → 최소 화면 | 완료 (2026-11-10, ADR 0007: 검색 hit@4 1.00, 진료 권고 재현율 0.96~1.00) |
| 5 | 깊게, 의미 충실도 측정 중심 ([ADR 0008](adr/0008-5단계-의미-충실도-측정-중심.md)): 단위 테스트 CI → 지표 재정의와 처음 보는 양식 기준선 → LLM 채점기·보정셋 → 두 경로로 분리([ADR 0010](adr/0010-해설-두-경로-분리와-후속-질문.md)): 채점기 검증 → 판정 코드 보완 → 판정 해설을 조회로 확정 → 후속 질문 정답셋과 근거 문서 확장 → 후속 질문 경로의 검색 전후 비교(하이브리드·리랭킹) → 질문 가드레일 시험 | 완료 (2026-11-12, ADR 0011: 후속 질문은 시험 통과 규칙 미달, 진단 거절을 "규칙 또는 LLM"으로 보완하고 한계로 공개) |
| 6 | 화면 개편(Spring 안에서 소개·해설 데모·품질 대시보드·운영 대시보드, taste-skill과 dataviz 사용), 결과 중심 README, 데모 예산 상한, 시연 영상. 저장소 공개 여부를 정한다 (CI는 5단계 처음으로 앞당김) | 진행 중 (2026-11-13, ADR 0012: 화면 4장·데모 예산 상한·시연 대본 완료, 저장소 공개(작성자 이메일 그대로). 시연 영상 녹화 남음) |
| 7 | 기능 2 Text-to-SQL. 6단계 뒤에 할지 정한다 | 완료 (2026-11-13, ADR 0013: 공공데이터 100만 행, LLM SQL + 구조 검사(JSqlParser) + 읽기 전용 계정 + 서버가 센 인원으로 작은 집단 숨김. 시험 32/34(깨끗한 기준값 27/34), 막을 요청 실행 0, 공격 문항 숨김 우회 0. 정답셋은 사용자 검토 뒤 v2) |

## 6. 협업 방식

- 큰 작업은 계획을 먼저 보여 주고 승인을 받은 뒤 진행한다.
- 커밋은 기능 하나에 하나씩 작게 한다. 커밋 전에 변경 요약을 보여 준다.
- 주요 설계 결정은 `docs/adr/`에 짧은 ADR로 남긴다(번호-제목.md).
- `docs/devlog.md`에 날짜별 진행 내용과 Claude Code 협업에서 잘 된 점, 막힌 점을 남긴다.
- 소프트웨어 설치처럼 시스템을 바꾸는 작업은 실행 전에 확인을 받는다.
