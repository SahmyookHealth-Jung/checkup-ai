## 2026-11-08 (1주차 1일): 환경 구성과 프로젝트 골격

### 한 일

- **개발 환경 점검**
  - 이 머신이 브리프의 가정(Apple Silicon)과 달리 **Intel Mac**(i7-8850H, 16GB)인 것을 확인했다.
  - Homebrew는 Intel macOS용 미리 빌드된 포뮬러를 더 이상 주지 않는다. 그래서 cask로 설치했다.
    - Ollama: `ollama-app` 0.40.15
    - JDK: `temurin@21` 21.0.13
  - Docker Desktop 28.0.4는 이미 설치돼 있었다.
- **스택 확정:** start.spring.io에서 Spring Boot 3.x가 빠져 있었다. 그래서 Boot 4.1.2 + Spring AI 2.0.1로 정했다([ADR 0001](adr/0001-기술스택-선정.md)).
- **구조 확정:** Gradle 멀티모듈(`core` / `report` / `app`, 이후 `stats`)로 정했다([ADR 0002](adr/0002-저장소-모듈-구조.md)).
- **Docker Compose:** PostgreSQL 18.6 + pgvector 0.8.7을 띄웠다. Flyway V1으로 `vector` 확장을 켰다.
- **Spring AI 연결 확인:** 통합 테스트 3개가 통과했다.
  - 앱 기동과 pgvector 확장 확인
  - bge-m3 임베딩이 1024차원으로 나옴
  - 의미가 가까운 문장의 코사인 유사도가 더 높음
- **Ollama 내부 구조 확인:** 구조는 `Ollama.app → ollama serve(:11434) → llama-server(러너)` 3단이다.
  - 러너는 요청이 올 때 모델을 메모리에 올리고, 5분 동안 요청이 없으면 내린다(keep_alive).
  - 모델은 Docker 이미지처럼 manifest와 sha256 이름의 blob으로 저장된다.

  - 응답을 캐시하고, 결과를 `eval/results/extraction/history.md`에 쌓는다.
- **검증 v1**(`validated-v1`): 반복 제거, 원문 대조, 상식 범위 검사, 누락 의심 줄 재요청.

### 오류 분석에서 배운 것
- **기준선 오류는 "지어내기"가 아니라 반복과 누락이었다.**
  - 목록 끝에서 같은 항목을 반복 출력했다.
  - 그 자리에서 추가 검사(OTHER)와 시력 행을 건너뛰었다.
  - 그래서 검증 설계를 "지어내기 차단" 중심에서 "반복 제거·누락 복구"로 바꿨다.
- **PDF 추출기(PDFBox 배치 보존 모드)는 칸 안 단어 사이에도 공백을 많이 넣는다**(`비활동성     폐결핵`). 모델이 이 공백을 칸 경계로 읽어 값이 잘렸다. 입력 토큰도 낭비된다.
- **검증 v1의 실패 원인**(Ollama 서버 로그의 요청별 소요 시간으로 추적)
  - 재요청 프롬프트에 결과지 전문을 넣었더니, 모델이 "이 줄만"이라는 지시를 무시하고 전체를 다시 추출했다.
  - sum-002에서는 반복 루프에 빠져 문맥(8192)이 찰 때까지 35분 50초 동안 출력했다.
  - 출력 토큰 상한과 앱 쪽 호출 시간 제한이 없어서 멈출 장치가 없었다.
- **temperature 0이어도 실행할 때마다 출력이 조금씩 다르다.** 기준선에서 맞힌 OTHER를 v1의 1차 추출에서는 놓쳤다. 그래서 파이프라인을 공정하게 비교하려면 같은 1차 출력에 검증만 적용해 비교해야 한다.
- 한 줄에 여러 항목이 있는 서술형은 줄 단위 커버리지 검사로 누락을 못 찾는다(시력).

  1. 누락 탐지가 제목("건강검진 3개년 추이 보고서"), 상담 안내 줄("1588-0000 (평일 09:00~18:00)"), 시력·청력 한 줄을 빠진 결과로 봤다.
  2. 모델은 재요청에서 줄 전체를 항목명으로 베꼈다. OTHER 검사(이름과 값이 같은 줄)는 이름이 줄 전체이면 늘 통과한다.
- **v2.2의 결론이 한 단계 더 나갔다.** v2.2에서는 "정밀도 장치는 일반화되고 재현율 장치는 과적합"이었다. 이번에는 재현율 장치(재요청)가 정밀도까지 깎았다. 처음 보는 양식에서는 재요청이 손해일 수 있다.
- **남은 누락 37건은 대부분 1차에서 이미 놓친 것이다.** 시력·청력 한 줄(4개 항목 × 5개 보고서), 3개년 칸에서 올해 값을 못 고른 추가 검사, 신체계측 일부다.
- **남은 FP 7건은 일부러 두었다.**
  - 값 "-"(3건): 소변 검사에서 "-"는 음성이라는 뜻이라, 빈 값 표시로 지우면 맞는 결과를 잃는다.
  - 지난해 값을 고른 경우와 오분류: 줄 모양만으로는 구분할 수 없다.

### Claude Code 협업

**잘 된 점**
- heldout-v2는 v2.3을 만들기 전에 생성해 두었고, 결과를 본 뒤에도 그 결과로 v2.3을 고치지 않았다. 그래서 0.845는 정직한 수치로 남았다.

- 코드 문구 대상(10개 항목)은 손으로 적은 목록이 아니라 "실제로 찾은 글 청크가 없는 항목"으로 정해진다.
- 5단계의 켜고 끄던 옵션(itemFilter, codeTemplates)을 없앴다. 평가 기록에는 근거 방식과 조회표 해시를 남긴다.

| | 조회 전 | 조회 후 |
|---|---|---|
| LLM 문장 | 437 / 436 | 176 / 176 |
| 다른 항목 근거만 인용 | 107 / 121 | 0 / 0 |

| 비용 / LLM 지연 | $0.071 / 6.0초 | $0.052 / 3.3~3.6초 |

- 통과율 1.0과 "다른 항목 근거 0"은 구조가 보장하는 값이라 대표 지표로 쓰지 않는다.
- 금지 표현 기록 1건: 공복혈당 문장이 "진단 및 검사" 절의 확진 기준을 설명했다. 단정은 아니지만, 이 절을 넣은 대가다.

**Claude Code 협업**
- Codex 적대적 리뷰(사용자 실행)가 high 1건을 냈다. 조회표에 적혀 있는지만 보고 LLM을 쓸지 정해서, 청크 파일이 바뀌면 기준표 행만으로 LLM 문장을 쓸 수 있다는 지적이었다.
  - Claude가 코드에서 사실로 확인했다. 청크 경로는 환경변수로 바뀌고, 저장소 테스트는 커밋된 파일만 지킨다.
  - 심각도는 medium으로 봤다. 지금 파일에서는 일어나지 않고, 일어나도 인용·숫자 검증은 돈다.
  - 반영: 실제 조회 결과로 판단한다. 시작 때 검증하자는 제안은 넣지 않았다. 실행 중에 파일이 바뀌는 경우를 놓치고, 앱 기동 조건을 바꾸기 때문이다.
  - 고치고 나니 기존 테스트 하나가 실패했다. 그 테스트가 지적된 동작(글 청크 없이 LLM 호출)에 기대고 있었다.
- `/codex:review`는 요청 문장을 받지 않아 실패했다. 초점을 주려면 `/codex:adversarial-review`를 쓴다.
- 구현 중 LDL 행 id를 잘못 적은 실수를 `EvidenceLookupTest`(실제 조회표와 실제 청크 파일 대조)가 잡았다.

**배운 점**
- 판단 근거는 설정이 아니라 실제 데이터여야 한다. "조회표에 있다"와 "근거를 찾았다"는 다르다.
- 구조를 바꾸면 형식 지표가 만점이 되기 쉽다. 그 만점은 개선이 아니라 구조의 결과라고 적어 둔다.

**판정 해설 경로는 여기서 닫는다.**

## 2026-11-12: ADR 0010 순서 6, 후속 질문 검색 기준선 (벡터만)

**만든 것:** `rag.run_followup_retrieval_eval`. 정답 절 기준 hit@k·recall@k·MRR, 범주별 1위 유사도, 개발/시험·작성자별 결과.

**적재:** 청크 169개, CPU 임베딩 3분 48초. 식별정보 제거기가 빈혈 청크 하나에서 이름을 잘못 감지했다(검사만 하고 바꾸지 않음. 근거는 시스템 메시지로 가서 원문이 유지된다).

**측정** (커밋 c4bbf8f, dirty=false, 답 가능 28문항)

| 질의 | hit@1 | hit@4 | recall@4 | MRR |
|---|---|---|---|---|
| 질문만 | 0.393 | 0.607 | 0.446 | 0.492 |
| 질문 + 항목 이름 | 0.571 | 0.857 | 0.652 | 0.698 |

- 사용자가 쓴 질문은 항목 이름을 붙이면 hit@4가 0.50에서 0.85가 된다. Claude 초안은 0.875 그대로다. 사용자 질문은 결과지 맥락에 기대고, 초안은 항목 이름을 질문에 적었다.
- 1위 유사도로는 답 불가를 가를 수 없다. 답 불가의 최대값(0.645)이 답 가능의 중앙값(0.639)보다 높고, 거절 질문의 유사도가 가장 높다.

**배운 점**
- 작성자별로 나눠 보고하기로 한 게 맞았다. 한데 합치면 Claude 초안이 사용자 질문의 어려움을 가린다.
- "근거 없음"을 유사도 임계값으로 막는 4단계 가드레일은 열린 질문에서 작동하지 않는다. 순서 7에서 다른 방법이 필요하다.
- 결과지 전체의 판정을 묻는 질문(fq-009)은 검색보다 판정 해설의 조회가 맞다. 질문 종류에 따라 경로를 나누는 것도 후보다.

**결정(사용자):** 기준선 질의는 질문 + 항목 이름. **다음:** 하이브리드 검색의 키워드 방식을 정한다.

## 2026-11-12: ADR 0011 (후속 질문 경로 설계)과 1단계 문맥 조건

**토의:** 사용자 요청으로 Opus 5.5와 Fable 5.2가 후속 질문 경로를 2라운드 토의했다. 세 키워드 방식에 묶지 않고 경로 전체를 열어 두었다.
- Fable이 던진 질문("정답셋의 항목 코드는 사람이 고른 값인데 서비스는 어디서 얻나")을 Opus가 계산으로 확인했다. 항목을 추론하면 문맥이 4배가 된다.
- 결론: 키워드 하이브리드 대신 "항목으로 범위 좁히기 → 범위 안 벡터 순위 → 절 채우기"로 간다. 무게는 거절·근거 없음 판단에 둔다. ADR 0011로 남겼다(사용자 채택).
- 예산(사용자): 남은 크레딧 $1.8 안에서 끝낸다. v1.3 재보정은 보류하고, 충실도 채점은 한 조건만 한다.

**만든 것:** `FollowupContextBuilder`, `ItemMentions`(항목 이름 사전), `GuidelineCorpus`(청크 파일 공용), 평가 API, `rag.run_followup_context_eval`. 단위 테스트 204개.

**측정** (커밋 86ab7a7, dirty=false, 답 가능 문항, 정답 절이 모두 들어온 문항 수)
- 항목 고름: 1만6천 자에서 개발 10/10, 시험 16/18.
- 항목 안 고름: 8천 자 개발 7/10, 1만6천 자 개발 9/10. 정해 둔 규칙대로 **예산은 1만6천 자**다.
- BM25(같은 범위, 8천 자): 개발 10/10. 모호한 질문 3개에서 "검사" 같은 단어로 "진단 및 검사" 절을 찾았다. 시험에서는 차이가 없다(13 대 13).

**배운 점:** 앱 밖 근사(토의)와 앱 안 측정이 달랐다. 근사로 결론을 내리지 않고 앱에서 다시 재기로 한 게 맞았다.

**다음 (사용자 결정):** BM25를 앱에 넣을지(ADR 0011 4절을 바꾸는 일). 그다음 2단계(답 만들기, 개발 몫).
