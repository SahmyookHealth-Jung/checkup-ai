# 개발 일지

## 2026-11-08 (1주차 1일): 환경 구성과 프로젝트 골격

### 한 일

- **개발 환경 점검**
  - 이 머신이 브리프의 가정(Apple Silicon)과 달리 **Intel Mac**(i7-8850H, 16GB)인 것을 확인했다.
  - Homebrew는 Intel macOS용 미리 빌드된 포뮬러를 더 이상 주지 않는다. 그래서 cask로 설치했다.
    - Ollama: `ollama-app` 0.40.15
    - JDK: `temurin@21` 21.0.13
  - Docker Desktop 28.0.4는 이미 설치돼 있었다.
- **스택 확정:** start.spring.io에서 Spring Boot 3.x가 빠져 있었다. 그래서 Boot 4.1.2 + Spring AI 2.0.1로 정했다([ADR 0001](adr/0001-기술스택-선정.md)).
- **구조 확정:** Gradle 멀티모듈(`core` / `report` / `app`, 이후 `stats`)로 정했다([ADR 0002](adr/0002-저장소-모듈-구조.md)).
- **Docker Compose:** PostgreSQL 18.6 + pgvector 0.8.7을 띄웠다. Flyway V1으로 `vector` 확장을 켰다.
- **Spring AI 연결 확인:** 통합 테스트 3개가 통과했다.
  - 앱 기동과 pgvector 확장 확인
  - bge-m3 임베딩이 1024차원으로 나옴
  - 의미가 가까운 문장의 코사인 유사도가 더 높음
- **Ollama 내부 구조 확인:** 구조는 `Ollama.app → ollama serve(:11434) → llama-server(러너)` 3단이다.
  - 러너는 요청이 올 때 모델을 메모리에 올리고, 5분 동안 요청이 없으면 내린다(keep_alive).
  - 모델은 Docker 이미지처럼 manifest와 sha256 이름의 blob으로 저장된다.

### 측정 (Intel CPU, Ollama 0.40.15, bge-m3 F16)

**시사점**
- 지연시간을 잴 때는 콜드/웜을 구분해야 한다.
- 문서 적재 때는 배치 처리와 임베딩 캐시를 고려해야 한다.
- 청크 크기는 4096토큰 안에서 정해야 한다.

### 결정
- Ollama는 컨테이너가 아니라 macOS 네이티브로 실행한다(Intel CPU 추론 성능 때문).
- 로컬 PostgreSQL 17(EDB 설치판)이 5432를 쓰고 있어 프로젝트 DB는 5433을 쓴다.
- 벡터 테이블 설계는 2주차로 미뤘다. 메타데이터와 키워드 검색 컬럼은 하이브리드 검색 설계와 함께 정한다.

### Claude Code 협업

**잘 된 점**
- 버전과 설정 키를 기억이나 블로그 대신 실제 소스에서 확인했다. 그래서 잘못된 가정 두 가지를 일찍 잡았다.
  - start.spring.io 메타데이터를 조회해 Boot 3.x가 없다는 것을 시작 전에 알았다.
  - jar 안의 `spring-configuration-metadata.json`을 읽어, Spring AI 2.0에서 `embedding.options.model`이 deprecated된 것을 확인했다. 1.x 예제를 그대로 따랐다면 경고가 났을 것이다.
- 환경 점검 단계에서 하드웨어(Intel)를 확인했다. 덕분에 모델 전략을 일찍 조정할 수 있었다.

**막힌 점**
- Homebrew 5.0.16에서 cask 조회가 내부 오류로 실패했다. `brew update`로 해결했다.
- `sudo` 비밀번호 입력란에 아무것도 표시되지 않아 입력이 안 되는 것처럼 보였다(정상 동작).
- **포트 충돌:** 사전 점검에서 `lsof`로 5432가 비어 있다고 판단했지만 실제로는 사용 중이었다.
  - 원인: `lsof`는 다른 사용자(postgres) 소유 프로세스를 보여 주지 않는다.
  - 교훈: 포트 점검은 `netstat -an`으로 한다.

## 2026-11-08~09 (1주차 1~2일): 결과지 추출 기준선과 검증 v1

### 한 일
- **설계([ADR 0003](adr/0003-결과지-추출-설계.md))**
  - 스키마: 항목 리스트 + 표준코드
  - 합성 데이터: 정답 JSON에서 렌더링
  - 입력: 텍스트·PDF 먼저
  - 추출: 구조화 출력 + 검증 + 재요청
- **스키마:** `ItemCode` 23개 + OTHER. `value`는 원문 문자열이고, 개인식별정보 필드는 없다.
- **합성 결과지 생성기**(`eval/synth`)
  - 레이아웃 3종으로 30개 보고서(항목 633개)를 만들었다.
  - 방해 요소를 넣었다: 전회 결과 칸, 소견 속 전회 수치, 나이 미표기.
  - 생성할 때 정답이 문서와 일치하는지 자동으로 검사한다. 이 검사로 정답 불일치 2건을 바로 발견해 고쳤다.
- **추출 기준선과 API:** `POST /api/reports/extract`. 로컬 모델은 qwen3:4b(임시, temperature 0, think off)로 두었다.
- **평가 스크립트**(`eval/extraction`)
  - 대표 지표는 **항목 F1(code+value)**이다(사용자 결정).
  - 응답을 캐시하고, 결과를 `eval/results/extraction/history.md`에 쌓는다.
- **검증 v1**(`validated-v1`): 반복 제거, 원문 대조, 상식 범위 검사, 누락 의심 줄 재요청.

### 측정 (Intel CPU, qwen3:4b Q4_K_M, 작은 평가셋 6개, PDF 입력)

| 항목 | 값 |
|---|---|
| 출력 생성 속도 | 자유 생성 6.0 tok/s, JSON 스키마 강제 4.2 tok/s, 실제 추출 약 3 tok/s |
| 보고서 1개 | 평균 301초, 입력 1,589토큰 / 출력 1,445토큰 |
| **기준선 F1** | **0.946** (P 0.961 / R 0.932), 지어낸 값 0건 |
| 검증 v1 F1 | 0.878 (P 0.991 / R 0.788). sum-002가 시간 초과로 실패 |
| 실패 1건 제외 비교 | 0.958 → 0.967 (정밀도 0.972 → 0.990) |

### 오류 분석에서 배운 것
- **기준선 오류는 "지어내기"가 아니라 반복과 누락이었다.**
  - 목록 끝에서 같은 항목을 반복 출력했다.
  - 그 자리에서 추가 검사(OTHER)와 시력 행을 건너뛰었다.
  - 그래서 검증 설계를 "지어내기 차단" 중심에서 "반복 제거·누락 복구"로 바꿨다.
- **PDF 추출기(PDFBox 배치 보존 모드)는 칸 안 단어 사이에도 공백을 많이 넣는다**(`비활동성     폐결핵`). 모델이 이 공백을 칸 경계로 읽어 값이 잘렸다. 입력 토큰도 낭비된다.
- **검증 v1의 실패 원인**(Ollama 서버 로그의 요청별 소요 시간으로 추적)
  - 재요청 프롬프트에 결과지 전문을 넣었더니, 모델이 "이 줄만"이라는 지시를 무시하고 전체를 다시 추출했다.
  - sum-002에서는 반복 루프에 빠져 문맥(8192)이 찰 때까지 35분 50초 동안 출력했다.
  - 출력 토큰 상한과 앱 쪽 호출 시간 제한이 없어서 멈출 장치가 없었다.
- **temperature 0이어도 실행할 때마다 출력이 조금씩 다르다.** 기준선에서 맞힌 OTHER를 v1의 1차 추출에서는 놓쳤다. 그래서 파이프라인을 공정하게 비교하려면 같은 1차 출력에 검증만 적용해 비교해야 한다.
- 한 줄에 여러 항목이 있는 서술형은 줄 단위 커버리지 검사로 누락을 못 찾는다(시력).

### 결정
- 평가는 당분간 로컬로만 한다. Haiku 평가는 나중에 한다(API는 구독과 별도로 크레딧 결제가 필요).
- 평소에는 작은 평가셋(6개, 약 1시간)으로 돌리고, 30개 전체(약 4~5시간)는 야간에 돌린다.
- 협업 방식: Claude가 구현하고 사용자가 리뷰한다. 분석은 근거를 보여 주며 단계별로 진행한다.

### Claude Code 협업

**잘 된 점**
- 결론을 추측하지 않고 증거로 원인을 좁혔다. 모델의 원본 응답, PDF에서 실제로 뽑힌 텍스트, Ollama 서버 로그의 요청 시간표를 직접 확인했다.
- 기준선 → 오류 분석 → 그 오류에 맞춘 검증 순서로 진행했다. 덕분에 개선 효과와 실패를 모두 숫자로 남겼다.

**막힌 점**
- 검증 기록을 **건수만** 남겨서 sum-001의 하락 원인을 확정하지 못했다. 다음 버전부터 상세 기록과 1차 출력 원본을 남긴다.
- 재요청 프롬프트 설계 실수(전문 포함)와 출력 상한 누락. 소형 모델에서는 "하지 마라"는 지시보다 입력 구성이 더 강하게 작용한다.
- Docker 메모리 설정을 바꾸면서 재시작된 뒤 DB 컨테이너가 뜨지 않아 앱 기동이 실패했다 → `restart: unless-stopped`로 해결.
- CPU 추론이 느려서(보고서 1개 5분, 평가 1회 1시간) 개선을 반복하는 속도가 크게 제한된다.
