# 0002. 저장소·모듈 구조: Gradle 멀티모듈

- 상태: 채택
- 날짜: 2026-11-08

## 맥락

- 저장소 하나에 기능 1(결과 해설 RAG)과 기능 2(Text-to-SQL)가 함께 있다.
- 두 기능이 함께 쓰는 공통 기반이 있다. AI 호출 관측·비용 기록, 가드레일, 예외 처리가 여기에 해당한다.
- 기능 2는 7주차에 추가된다. 그때 기능 1을 건드리지 않고 붙일 수 있어야 한다.

## 결정

백엔드를 Gradle 멀티모듈로 나눈다(A안).

```
backend/
├── core/     공통 기반 (Spring AI 추상화에만 의존)
├── report/   기능 1
├── stats/    기능 2 (7주차에 추가)
└── app/      실행 모듈: 조립 + 공급자 스타터 + 설정 + Flyway
```

- 의존 방향을 빌드가 강제한다: `report → core`, `stats → core`, `app → 전부`, `report ↛ stats`.
- 공급자 구현체(Ollama, Anthropic, pgvector 스타터)는 `app`만 가진다. 기능 모듈은 인터페이스만 안다.
- 공통 빌드 규칙(Java 21, BOM, 테스트 분리, `.env` 주입)은 `buildSrc`의 `checkupai.java-conventions` 플러그인 하나에 모은다. 버전은 `gradle/libs.versions.toml`에서만 관리한다.
- 최상위에는 `backend/`, `eval/`(Python), `frontend/`, `data/`, `docs/`를 둔다.

## 검토한 대안

- **B안: 단일 모듈 + Spring Modulith**
  - 장점: 패키지로 모듈을 나누고 `ApplicationModules.verify()` 테스트로 경계를 검사한다. 설정이 가장 단순하다.
  - 기각 이유: 경계 위반이 컴파일이 아니라 테스트 단계에서 걸린다. "공통 기반 재사용"이 디렉터리 구조로 드러나지 않는다.
- **계층형 단일 모듈(controller/service/repository)**
  - 기각 이유: 기능이 늘수록 경계가 흐려진다.

## 결과

**좋은 점**
- 기능 2를 추가할 때 `settings.gradle.kts`에 `stats`를 넣고 `core`에만 의존하게 하면 된다.
- 기능 모듈이 공급자에 의존하지 않으므로 모델 교체가 설정만으로 가능하다.

**감수할 점**
- 1주차 빌드 설정량이 늘어난다(buildSrc, 모듈별 빌드 파일).
- 라이브러리 모듈(`core`, `report`)에서 스프링 컨텍스트 테스트를 하려면 테스트용 `@SpringBootConfiguration`이 따로 필요하다.
- 통합 테스트는 `@Tag("integration")` + `./gradlew :app:integrationTest`로 분리한다. 기본 `build`는 외부 의존 없이 통과해야 한다.
