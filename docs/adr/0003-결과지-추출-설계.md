# 0003. 결과지 추출 설계

- 상태: 채택
- 날짜: 2026-11-08

## 맥락

- 기능 1의 첫 단계로, 검진 결과지에서 검사 수치를 뽑아 JSON으로 구조화해야 한다.
- 이 JSON은 이후 RAG 검색의 키(어떤 항목의 가이드라인을 찾을지)가 되고, 해설의 입력이 된다.
- 추출이 틀리면 뒤의 해설이 모두 틀린다. 특히 LLM이 결과지에 **없는 값을 지어내는 것**이 의료 맥락에서 가장 위험하다.
- 실제 수검자 결과지는 쓸 수 없다. 정확도를 재려면 정답이 붙은 합성 결과지가 필요하다.
- 로컬 모델은 Intel CPU에서 돌아서 느리고 작다(ADR 0001).

## 결정

### 1. 스키마: 항목 리스트 + 표준코드

```json
{
  "examDate": "2026-10-14",
  "examType": "GENERAL",
  "sex": "MALE",
  "age": 43,
  "items": [
    { "code": "FASTING_GLUCOSE", "rawName": "식전혈당(공복혈당)", "value": "112",
      "unit": "mg/dL", "referenceRaw": "70~99", "centerJudgment": "정상B(경계)" },
    { "code": "URINE_PROTEIN", "rawName": "요단백", "value": "음성",
      "unit": null, "referenceRaw": "음성", "centerJudgment": "정상A" },
    { "code": "OTHER", "rawName": "요산", "value": "7.9",
      "unit": "mg/dL", "referenceRaw": "3.5~7.2", "centerJudgment": null }
  ]
}
```

- `code`: 국가 일반건강검진 항목 23개 + `OTHER`를 enum으로 강제한다. 동의어(식전혈당, FBS, Glucose)는 같은 코드로 모인다.
- `value`: **원문 문자열 그대로** 받는다(`"112"`, `"음성"`, `"1+"`). 숫자 변환과 단위 환산은 코드가 한다.
  - LLM에게는 "베끼기"만 시킨다. 그래야 값이 원문에 실제로 있는지 기계적으로 대조할 수 있다.
  - 요단백이나 흉부방사선처럼 숫자가 아닌 결과도 같은 필드에 담긴다.
- `age`: 원문에 적힌 나이를 그대로 받는다. 연령대 구간 계산은 코드가 한다(LLM에게 계산을 시키지 않는다).
- **개인식별정보는 스키마에 필드가 없다.** 이름, 주민번호, 생년월일, 주소, 연락처는 구조적으로 추출되지 않는다.
- 이번 회차 결과만 뽑는다. 결과지의 "전회 결과" 칸은 추출 대상이 아니다.

### 2. 합성 데이터: 정답 JSON → 문서 렌더링

- 정답 JSON을 먼저 만든 뒤, 레이아웃 템플릿으로 텍스트와 PDF를 찍어낸다. 그래서 정답 라벨이 자동으로 생긴다.
- 레이아웃은 3종이다. 공단 표준 서식형, 기관 요약표형(전회 결과 칸과 영문 약어 포함), 목록+소견형.
- 평가용이므로 인구 분포의 현실성보다 **경우의 수 커버리지**를 우선한다.
  - 정상, 경계, 이상 값
  - 항목 누락(예: 지질 검사는 4년 주기)
  - 동의어 항목명
  - 국가검진 외 추가 항목
  - 전회 결과나 소견 문장 속 숫자 같은 **방해 요소**
- 시드를 고정해 같은 데이터를 재현할 수 있게 한다.
- 생성기의 판정 구간은 합성 문서에 찍을 값을 고르는 용도일 뿐이다. 해설(RAG)의 근거로는 쓰지 않는다. 출처를 확인하기 전까지 "임시값"으로 표시한다.

### 3. 입력 형식: 텍스트 + 텍스트 PDF 먼저

- PDF는 글자 층을 추출(PDFBox)해 LLM에 넘긴다.
- 이미지(스캔, 폰 사진)는 비전 모델이 필요하다. 로컬 CPU로는 비현실적이라 3주차 이후 Claude 비전 전용으로 추가한다.

### 4. 추출 방식: 구조화 출력 + 코드 검증 + 재시도

1. JSON 스키마로 출력을 강제한다(구조화 출력).
2. 코드로 검증한다.
   - 타입과 형식
   - **원문 대조**: 추출한 `value`가 원문에 실제로 있는가
   - 단위와 값 범위의 상식 검사(생리적으로 불가능한 값)
3. 실패한 항목만 오류 설명과 함께 다시 요청한다(최대 횟수 제한).

**구현 순서:** "구조화 출력만"으로 만든 **기준선을 먼저 측정**한다. 그다음 검증과 재시도를 붙여 개선 폭을 수치로 남긴다.

## 검토한 대안

- **고정 필드 스키마**
  - 장점: 가장 단순하고 평가도 쉽다.
  - 기각 이유: 종합검진의 추가 항목을 담을 수 없고, 항목이 늘 때마다 스키마를 바꿔야 한다.
- **자유 항목 리스트(코드 없음)**
  - 장점: 추출이 쉽다.
  - 기각 이유: 동의어를 나중에 정규화해야 하고, 평가할 때 항목을 맞추기 어렵다.
- **LLM이 결과지 생성**
  - 장점: 결과지가 다양하다.
  - 기각 이유: 정답을 사람이 검수해야 하고, 수치 조합이 비현실적일 수 있다.
- **처음부터 이미지 입력**
  - 장점: 실제 사용 장면에 가장 가깝다.
  - 기각 이유: 개발 내내 API 비용이 들고, 로컬로 개발할 수 없다.
- **규칙 기반 파서 우선**
  - 장점: 정확하고 빠르다.
  - 기각 이유: 레이아웃마다 규칙이 필요하고, 포트폴리오 목적과 거리가 있다.

## 결과

**좋은 점**
- 정답이 자동으로 생기는 평가셋이 생긴다. 그래서 1주차부터 "기준선 → 개선" 수치를 낼 수 있다.
- 원문 대조 덕분에 "지어낸 값"을 런타임에서 잡을 수 있고, 그 비율을 지표로 잴 수 있다.
- 개인식별정보는 스키마 차원에서 배제된다.

**감수할 점**
- 코드를 잘못 매핑하는 오류 유형이 생긴다. 이 오류는 평가에서 따로 센다.
- 합성 문서는 실제 결과지의 지저분함(표 깨짐, 스캔 번짐)을 덜 재현한다. 이미지 입력을 추가할 때 보강한다.
- 검증과 재시도로 지연시간과 토큰이 늘어난다. 이 비용도 함께 측정한다.
